## Findings

1. **`design: none` names two different homes for the same owner amendment** — blocking. The protocol's Waiver rule says a design bypass is an owner amendment "recorded in the design record" (`PRINCIPLES.md:105-107`). The `design: none` rule that is meant to scope every design record says both that "every reference to a design record in this file resolves to the implementation review file" **and** that "an owner amendment that would otherwise bypass a design stage is recorded in the project slot" (`PRINCIPLES.md:132-136`). For a `light` run those two sentences send one and the same amendment to two different places: the implementation review file (via the Waiver reference plus the resolution clause) and the project slot (`:136`). The clause is the one the design 003 review required to be settled (`design/003-parametrizable-scaffold.md:61-67`), but the resolution sentence it landed with contradicts it. The completion note has the same shape: `PRINCIPLES.md:119-126` says "the change's record", `design/README.md:34-39` places it in the design record, and `reviews/README.md:27-33` names the implementation review file only for Claude; no clause states it for an OpenCode `design: none` run. Fix the scoping sentence so the light run has exactly one stated home for a bypass amendment and for the completion note. This is central to the rulebook, not a separate concern.

2. **A `light` run ships a design instruction and a `design/README.md` link its preset never generates** — non-blocking. `presets/light.json:3-9` drops `design/README.md`, yet the shipped `AGENTS.md:31-36` still opens with "Before any implementation, write the design record (`design/NNN-<slug>.md`; format in [`design/README.md`](design/README.md))", and `PRINCIPLES.md:21` still names `design/README.md` as the owner of the design-record format. I generated `light` from r4 into a temp directory: it contained five source files, no `design/README.md`, and the AGENTS stage-1 text and the PRINCIPLES map row were present verbatim. The later sentence `AGENTS.md:44-46` ("a project whose slot records `design: none` has no design stage") resolves the process, so a careful builder is not stuck — but the run links a file it does not have. Qualify the stage-1 text (or ship the format file) so the generated run does not instruct a missing artifact.

3. **`ROADMAP.md` restates the mode processes and invents an unowned "brief"** — non-blocking. `ROADMAP.md:42-44` says "The shaping *is* the design stage — in OpenCode mode it becomes the design record, in Claude mode the brief." The Claude Code process is owned by `CLAUDE.md`, which states there is no design stage and no design record (`CLAUDE.md:19-20`); the word "brief" appears nowhere else in the tree, so it is an artifact no owner defines. The same section also says "the shaping and the design stage still happen" (`ROADMAP.md:21-24`), which is false for a `design: none` project. The ownership map (`PRINCIPLES.md:16-17`) puts these ideas with the adapters; `ROADMAP.md` should point there rather than restate them.

4. **`BACKLOG.md` restates the bootstrap rule inaccurately** — non-blocking. `BACKLOG.md:3-7` says a change to "a harness file ... or to the tool takes both stages through the bootstrap: a design record reviewed to AGREE, then the implementation reviewed to AGREE." The owner is `PRINCIPLES.md:137-139`: only a harness-file change "that changes what a builder must do or how the process works" takes the mode's review — both stages in OpenCode, the review alone in Claude, and "a pure typo takes neither." BACKLOG drops the trigger, the typo exception and Claude's single stage. It also enumerates the harness files while the owner does not, so the two lists can drift.

5. **`README.md` restates the assignment table and the merge policy, both owned elsewhere** — non-blocking. `README.md:4`, `:12` and `:42` name "DeepSeek implements, Luna reviews" — the assignment table owned by `AGENTS.md:9-27`, whose own rule says the table is the current assignment and is updated when it changes. Changing the assignment would silently leave the README stale. `README.md:16` also flattens Claude's process, which allows an external cross-family process (`CLAUDE.md:15-18`), into an unqualified "no cross-family reviewer". `README.md:59-61` restates the merge policy owned by `PRINCIPLES.md:127-131`. The README should describe and point, not duplicate.

6. **Live and historical `docs/` references are stale after the archive move** — non-blocking. `CLAUDE.md:39-41` says the harness source repository's own rules "are README.md and docs/", but at r4 the only content under `docs/` is `docs/archive/` (`ls-tree`); `README.md:84-86` confirms the analysis is archived. In the records, `design/002-harness-release-2.md:171` links `../docs/08-geoclick2027-harness.md`, and `design/003-parametrizable-scaffold.md:199,258,261,289,314` cite `docs/08`, `docs/05-harness-competition.md` and `../docs/06-testing-the-harness.md`; none exist at those paths (`08`/`06` are under `docs/archive/`, and `05` is absent).
